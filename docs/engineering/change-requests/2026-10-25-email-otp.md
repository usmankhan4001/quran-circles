# Change request: the sign-in code goes by email (Resend), not WhatsApp

Requested by: the owner (Muhammad), through the coordinator session; done on branch `lane/auth/email-otp`
Contract: schema (`users`, `otp_challenges`, `coordinator_invites`; migration 0015), endpoints (`auth.requestCode`, `auth.verifyCode`, `me.update`, `adminRoles.invite`), messaging (new provider), sign-in screens in all three apps
What I need: email as the identity and one-time-code channel, delivered by Resend. WhatsApp sign-in is switched off behind a flag, not deleted. The WhatsApp number is required at sign-up and kept for reminders and coordinator contact, but not verified by a code.
Why: WhatsApp templates and approval block the pilot; email works today and the domain is verified in Resend.
Affected lanes: auth-scopes (`apps/api/src/auth/`, `modules/auth/`), messaging (`packages/messaging/`), contracts and db (`packages/contracts`, `packages/db`), user-app, admin-app, console, platform (`infra/`), i18n.
Workaround meanwhile: none needed; the legacy path still works with `AUTH_PHONE_SIGN_IN=true`.

## What changed

**Identity.** A person is identified by a verified email (lower-case, unique among non-null values) or, for older accounts, a verified phone. `users.phone_e164` stays `NOT NULL UNIQUE`: it is now the mandatory WhatsApp number (any country, E.164). `users.phone_verified_at` is nullable (null for a number nobody proved), `users.email_verified_at` is new, and a check requires `(email and email_verified_at) or phone_verified_at`. Existing phone users keep working unchanged.

**Sign-up.** A new email account must send its WhatsApp number with the code request (`otp_challenges.claimed_phone_e164`). Verify then refuses with `phone_required` (no number sent) or `phone_in_use` (already another account's); the code stays usable. A typed number never links to an existing phone-only account (that would let anyone claim a number by typing it): linking an old account to an email is a later, separate step.

**Invites.** `coordinator_invites.email` is new. An invite is accepted by the invitee's verified email, or by phone only when `phone_verified_at` is set. A typed (unverified) number never accepts an invite. The console invite form now asks for the email (required in the form, optional in the contract so old rows and clients still parse), and `bootstrap-admin` takes `--email`.

**Limits.** Rate limits, daily caps, resend wait and the five-minute expiry are unchanged, counted per target (email or phone). `AUTH_PHONE_SIGN_IN=true` brings WhatsApp sign-in back next to email (default off). With it off, a phone-only request is refused with `validation_failed` `{path: 'email', code: 'email_required'}`.

**Messaging.** `@qc/messaging` gets `ResendEmailProvider`, a development `ConsoleEmailProvider` (masks the address; used when no key is set outside production) and `EmailRenderer`, a hook taking (template name, locale, data) with only a plain placeholder for the code email (`renderPlainEmail`). The real email templates are a separate thread and plug into the hook. Production live mode refuses to start without `RESEND_API_KEY`. The WhatsApp reminder path is untouched. One constant, `MAIL_DOMAIN` (`qurancircles.doraquran.pk`), gives the default sender `Quran Circles <notifications@qurancircles.doraquran.pk>` and the contact addresses `support@` and `privacy@`.

**Apps.** Member app: email sign-in; sign-up, the join sheet and the registration pledge ask for email and WhatsApp number; the profile shows the email and lets the WhatsApp number be edited. Coordinator app and console: email field, plus an optional WhatsApp field labelled "first sign-in only" (sent with the request; if the server says it is needed, the screen asks for it). All strings are in EN and UR together (Urdu is draft).
