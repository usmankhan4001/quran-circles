### What changed in the repository for it

- `infra/docker-compose.dokploy-prod.yml`: the production override, the same pattern as staging. Dokploy's Traefik owns ports 80 and 443, so the production `proxy` is parked and `web` (Caddy on plain HTTP, PWA and console baked in) is routed by Traefik labels. No seed, load-test or restore-check services.
- `infra/caddy/Caddyfile.dokploy-prod`: production routes, headers and CSP over HTTP, api and worker by the aliases `qc-prod-api` and `qc-prod-worker`.
- `infra/docker/proxy-staging.Dockerfile`: takes the Caddyfile, the Maps web key and the VAPID public key as build arguments (staging keeps its defaults).
- **Real client addresses** (`Caddyfile.dokploy-prod` and `Caddyfile.staging`). Through Cloudflare, cloudflared and Traefik the api saw one address, the Traefik hop, for everybody. The sign-in limits per address (30 code requests an hour, 40 code checks per 15 minutes) and the request buckets would then have been shared by every person in the pilot, and sign-ins would start failing after about 30 an hour. Caddy now takes the client from `CF-Connecting-IP` (or Traefik's `X-Forwarded-For`, rightmost entry) and passes it to the api as the single `X-Forwarded-For` entry. Checked with Caddy 2.10.2 against an echo server: Cloudflare header, Traefik header and a forged chain each give the expected address. Limit: someone who reaches Traefik directly, bypassing Cloudflare, can choose the address the per-address limits see; the per-number and global sign-in caps are not affected.
- **OpenStreetMap tiles in the CSP** (change request `2026-10-25-osm-map-tiles-csp`): `https://tile.openstreetmap.org` added to `img-src` in all three Caddyfiles, so the keyless map shows on the web.

### Backups

The repository's `backup.sh` needs root and cron on the host, which a shared Dokploy host does not give. For the pilot, use Dokploy's own backups:

1. Owner creates a private bucket (Cloudflare R2 fits, the domain is already there) with an access key that can write but not delete, and adds it in Dokploy as a destination (Settings, S3 Destinations).
2. Then Claude adds a daily backup of the compose service's `postgres` (database `qc`, user `qc`) and a daily volume backup of `poster-files`, keeping 14 days, and runs one restore into a scratch database to prove it.

Dokploy's dumps are not age-encrypted as SEC-19 asks; keep the bucket private with encryption at rest, and move to `backup.sh` when production gets its own server.

## 2. Google Maps keys

In its Google Cloud project, add `https://qurancircles.doraquran.pk/*` to its website restrictions, or the map falls back to the keyless OpenStreetMap map. A website-restricted key does not work in the Android Maps SDK, so the Android app needs a second key; the target setup is two keys:

| Key     | API restriction      | Application restriction                                                                                   | Where it goes                                                           |
| ------- | -------------------- | --------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |

Needed from Meta Business Manager: a verified business, a WhatsApp Business Account with the sending number registered, a system user with a permanent token (`whatsapp_business_messaging`), the app secret, and the message templates approved (the catalogue is migration 0013). SMS fallback has no provider chosen; with `CODE_SMS_FALLBACK` on and no gateway, a person whose number is not on WhatsApp cannot sign in.

## 5. Android build and Play release

### Accounts and signing

- Expo account: the existing one made for WayApp (owner's decision). From `apps/user-app`, `eas init` prints the project id: put it in an EAS environment variable `EAS_PROJECT_ID` and in your shell when running `eas` locally.
- Signing: let EAS create and keep the upload keystore (`eas credentials`), and enrol in Play App Signing when creating the app. Download a copy of the upload keystore and keep it offline.
- Build: `eas build -p android --profile production` (AAB, version code incremented by EAS). `--profile preview` makes an APK for passing round by hand.
- `eas.json` sets `submit.production` to the **internal** track as a draft. Google requires the very first upload of a new app through Play Console by hand; after that `eas submit -p android` uses a Play service account (Play Console, Users and permissions, invite the service account with release rights; give the JSON to `eas credentials`).

Personal developer accounts created after November 2023 must run a closed test with at least 12 testers for 14 days before production access. The project notes say the Play account is an organisation account, which is exempt; check Play Console's dashboard to be sure.
