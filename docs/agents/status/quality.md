## Gate 5 push drain: cause, fix and a fairer measure (2026-10-18)

Orchestrator request after staging's Gate 5 load run failed "push drain per second" in every step (840 rows drained in 18.4, 12.3, 40.6 and 41.7 s). Worker side in `docs/agents/status/messaging.md` (same date). Files here: `tests/load/src/load/push.ts`, `push.test.ts`, `run.ts`, `format.ts`, `src/local/dbstats.ts`, `k6/ramadan-evening.js`.

- **Reproduction.** A scratch harness (not in the repository) ran the real API and worker with **production worker defaults** (no `WORKER_POLL_MS`, `WORKER_PUSH_*` defaults, `MESSAGING_MODE=fake`), the worker pinned to one core and the API to another (`taskset`), Postgres 16 on the same 4-CPU box, and `pnpm --filter @qc/load load --worker-url` (the remote `/healthz` probe, as on staging), 800 push rows per burst, the four steps of `scenario.json`. Ground truth afterwards from `message_outbox` per update (database clock, seconds from the post).
- **Before** (worker and probe as on main): reported drain 8.2 / 21.1 / 44.2 / 31.4 s (10 / 25 / 50 / 100 VUs), all over threshold, the same shape as staging. On the database clock the same bursts were written 0.49 / 3.76 / 1.75 / 3.93 s after the post, first sent 0.95 / 4.10 / 2.19 / 4.73 s, **last sent 2.36 / 5.20 / 3.40 / 7.29 s**; send span 1.1 to 2.6 s; every row on attempt 1.
- **Cause.** (1) The measure: remotely the probe read the worker's global counts and timed the burst to the last growth of the global sent count. The virtual users' registration confirmations (about 300 WhatsApp sends per run) keep it growing through the step, so the reported time stretches to the end of the VUs' window (at 50 and 100 VUs: the ~34.5 s left after the post plus the last confirmations, hence ~40 s on staging). This is most of the miss. (2) The worker: the fan-out waited for the next 5 s poll pass, up to 5 s of the 8.4 s that 840 rows at 100 a second allow. (3) The rate is latency-bound for small bursts: rows divided by seconds from the post's answer includes the fixed wait before the first send, so 840 rows can only pass if the whole burst ends within 8.4 s, however fast the senders are.
- **Fix in `tests/load`.** The healthz probe asks `/healthz?update=<id>`; a worker that answers it gives the update's own rows and times, and the burst is then judged exactly like the local database probe (drained when the fan-out is done and nothing is queued or sending; no baseline subtracted; rows from the final counts). An older worker falls back to the global rule, now labelled "global counts" in the log and the summary as over-reporting. Both probes now return the database-clock times, and the report adds `perUpdate` and `timeline` (`writtenS`, `firstSentS`, `lastSentS`, `sendPerSecond` = rows from the first send to the last). The k6 script does the same (new trends `qc_push_last_sent_s` and `qc_push_send_per_s`, reported, no threshold). **No threshold changed:** `push drain per second` is still rows divided by seconds from the post's answer, at least 100.
- **After** (new worker with production defaults, new probe, same harness, while another test suite was using the CPUs): **drained in 2.1 / 3.2 / 2.0 / 3.1 s (381 / 250 / 400 / 258 a second), every step within every threshold**; written 0.35 / 0.56 / 0.23 / 0.77 s after the post, last sent 1.84 / 2.38 / 1.48 / 2.83 s; senders' rate from the first send 738 / 530 / 944 / 477 a second; 800 of 800 sent each time, attempt 1, 0 `worker_lost`.
- **Tests.** `push.test.ts` +5: drained on the update's own rows while the global sent count keeps growing (no baseline subtracted, rows from the final counts, timeline and send rate, baseline read global and every later read per update); keeps waiting while the update's rows are queued and times out rather than guess; the probe asks `?update=<id>` and parses the block; falls back to global counts for a worker without it or an unknown update (`null`); no send rate below two sends and no timeline without times. `@qc/load` 40 tests; typecheck, eslint and prettier clean.
- **Proposal for the owner (thresholds are not changed here).** For small bursts "rows / seconds from the post" mixes a fixed latency with throughput: at 840 rows it is an end-to-end budget of 8.4 s, at 50,000 rows a throughput of 100 a second. Fairer: (a) **send rate** from the first send to the last of at least 100 a second (reported now as `timeline.sendPerSecond`), plus (b) an **end-to-end budget**, for example the first push within 5 s of the post and the last within `5 s + rows / 100`. Recorded as a question for `docs/product/decisions.md`; the current threshold stays the gate meanwhile, and with this fix it passes on its own terms.
- **Staging must re-run** Gate 5 load after deploying the new worker image (wake probe, `/healthz?update=`) and rebuilding the `gate5` tools image with this `tests/load`. Check the log line says no "(global counts)" and shows the timeline. Do not set `WORKER_POLL_MS` on staging (its meaning changed; see messaging status).
- Questions for the orchestrator: accept the proposed send-rate plus end-to-end measure for a later threshold change, or keep the current one? platform lane to add `WORKER_WAKE_MS` and the new `WORKER_POLL_MS` default to `infra/ENV.md` and the env examples.
- Fix (2026-10-18): `local` crashed with "Invalid time value" because `ms.reduce(Math.min)` also passed the index and array (NaN); now `pickTime` in `src/local/dbstats.ts` wraps the reducer and returns null for no times, with a regression test in `src/local/dbstats.test.ts` (3 of its 5 tests fail on the old code); no other bare `reduce(f)` in `tests/load`; `@qc/load` 45 tests, typecheck, eslint and prettier clean.
