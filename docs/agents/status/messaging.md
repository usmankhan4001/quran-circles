## Done (2026-10-18: Gate 5 push drain on staging, orchestrator request)

- **Cause** (reproduced locally with production worker defaults, worker pinned to one core with `taskset`, API on another, the remote `/healthz` probe as on staging; 800 push rows per burst; numbers below):
  1. **Mostly the measure.** Remotely the load test read the worker's _global_ `/healthz` counts and called the burst drained once the global sent count stood still for 5 s, timing it to the last growth. The virtual users' registration confirmations (WhatsApp, about 300 sent per run in fake mode) keep that count growing all through the step, so the "drain" ran to the end of the VUs' window: 40.6 and 41.7 s on staging at 50 and 100 VUs is the 34.5 s left of the step after the post plus the last confirmations. On the database clock the same bursts finished 2.4 to 7.3 s after the post.
  2. **Then the 5 s poll.** The update's push rows were written only at the next poll pass (`WORKER_POLL_MS` 5 s): 0.5 to 3.9 s after the post in the runs below. With 800 to 840 rows a threshold of 100 a second leaves 8.4 s end to end, so a full poll interval of wait was a real share of it. Sending itself was never the bottleneck: 1.1 to 2.6 s for 800 rows (300 to 700 a second) on one core.
  3. **Not CPU contention.** The worker's send span grew from 1.1 to 2.6 s between 10 and 100 VUs, well inside the budget.
- **Fix (`apps/worker`).**
  - Wake probe (`outbox/repo.ts` `findPendingWork`): one read-only statement of three `EXISTS` index probes (a pending update fan-out, a due `queued` row, a `sending` row with a lost lease), no transaction, no write. The poll loop (`runtime.ts`) runs it every `wakeIntervalMs` (`WORKER_WAKE_MS`, default 1 s) and starts a full pass (fan-out, reclaim, claim) at once when it finds work; after a pass with more to do it passes again after `busyIntervalMs` without probing, as before. `dispatchIntervalMs` (`WORKER_POLL_MS`) is now only the safety net, the longest without a full pass: default **30 s** (was 5 s). A failed probe falls back to the pass and logs `outbox.wake_probe_failed`. `WORKER_WAKE_MS=0` gives the old loop (a pass every `WORKER_POLL_MS`). New counters `passes` and `wakeups` in `runtime.stats()` and `/healthz` `metrics`.
  - Idle database load goes **down**, not up: measured with `pg_stat_statements` over one idle minute, the worker's own statements fell from 331 to 105 a minute (pg-boss's own polling, 863 and 807 a minute, is about the same), commits from 968 to 891. LISTEN/NOTIFY would bring the idle probe to zero, but needs a trigger (a `packages/db` migration, contracts lane) or a `pg_notify` from the API (api-core): proposed below, not done.
  - `/healthz?update=<uuid>` (`whatsapp/handler.ts`, `main.ts`, `outbox/repo.ts` `updatePushProgress`): adds that update's push rows, counts and database-clock times only (`pushPending`, `postedAt`, `writtenAt`, `firstSentAt`, `lastSentAt`, `rows`, `queued`, `sending`, `sent`, `other`, `workerLost`, `maxAttempts`; `null` for an unknown update). Anything but a UUID gets 400 before the database is touched; without the parameter `/healthz` is unchanged. It scans `message_outbox` (no index on `update_id`), so it is for the load test and diagnosis, not the container health check.
- **Measured** (`docs/agents/status/quality.md`, "Gate 5 push drain"): the same run as staging's shape went from 8.2 / 21.1 / 44.2 / 31.4 s reported (all failing 100 a second) to **2.1 / 3.2 / 2.0 / 3.1 s** (381, 250, 400, 258 a second; all four steps within every threshold), rows written 0.2 to 0.8 s after the post.
- **Tests.** `runtime.test.ts` +7: the probe finds nothing when idle, nor rows due later, finished, or sending on a live lease; it sees a pending fan-out, a due row and a lost lease each on its own; with a one-minute safety net and a 100 ms probe the loop writes and sends a posted update's pushes within seconds, and wakes for a row queued while idle after passing only once while nothing was due (both fail on the old loop, which waits the interval); a failing probe falls back to the pass and logs it; with the probe off it passes on the interval; `updatePushProgress` counts and times, `null` for an unknown update. `webhook.test.ts` +1 (a valid `?update=` reaches the health check, `''`, junk and injection-shaped values get 400 and never reach it). `config.test.ts` +1 (`WORKER_WAKE_MS` 0 or 100 to 60000; new defaults). `@qc/worker` 265 tests in 13 files; typecheck, eslint and prettier clean.

## Done (2026-10-18: load-test push livelock, quality WP12 finding)

- **Cause.** The dispatcher claimed up to 50 rows per tick with no regard to what the senders could finish (about 20 a second: batch 10 x concurrency 4, then a 2 s pg-boss wait). In a 15,050-row burst the 5-minute leases ran out on the queue, `reclaimStale` requeued the rest, and the queue then spent its slots on stale jobs.
- **Fix (`apps/worker`).**
  - In-flight limit per lane (`outbox/dispatcher.ts`): before claiming, the dispatcher counts every worker's `sending` rows for the lane (`countInFlight`) and claims only up to the limit, in statements of 500, until the limit or the due rows run out. The rest wait as `queued` (no lease, no attempt spent). Defaults: push 2,000, WhatsApp/SMS 100. While a lane is full the loop looks again every `busyIntervalMs` (1 s) instead of `WORKER_POLL_MS`.
  - Two lanes (`outbox/repo.ts` `SendLane`): push rows go to a new pg-boss queue `outbox-send-push` (batch 50, 4 batches per node, 10 sends at once per batch, 0.5 s poll, `burstWhenBatchFull`). WhatsApp and SMS stay on `outbox-send`, one message at a time per batch with the SEC-02 cap and budget checked per message as before. WhatsApp is claimed first, so a push burst never delays a reminder. Both queues share `outbox-send-dead` and the retry settings.
  - Taking a batch (`takeForSending`): one statement per batch takes the rows still `sending` for the job's attempt and the claim's lease (now carried in the job as `lease`), and renews the lease. Stale, duplicate and unknown jobs drop out of that statement and cost no send slot. Only one sender can take a claim (the renewed lease always moves, by at least 1 ms). A row being sent is never reclaimed, because its lease restarts when sending starts. Jobs queued before this change (no `lease`) are matched on the attempt alone, as before. `processJob` uses the same take; the new `processJobs(deps, jobs, { parallel })` sends a batch with bounded parallelism and returns outcome counts and the first database failure (the batch is still failed for a pg-boss retry).
  - A lost lease is logged as `outbox.worker_lost` at **error** level (it replaces the warn `outbox.reclaimed`), and counted. `/healthz` keeps `details` (counts by status, which the load test reads) and adds `metrics`: `claimed`, `workerLost`, `workerLostDead`, `staleJobs`, `sent`, `requeued`, `failed`, `dead`, `updatePushes`, `updatePushRows`, `updatePushesPending`. `runtime.stats()` returns the same counters.
  - Update push fan-out (api-core finding, see `status/api-core.md`): each poll pass first runs `fanOutPendingUpdatePushes` (`@qc/db`) for at most one update (log `updates.pushes_written`, counts only; a failure is logged as `updates.push_fanout_failed` and dispatching carries on). `runtime.fanOutNow()` does it on demand.
  - Unchanged: provider retry and backoff on the row (`decideRetry`, a provider's retry-after honoured), the push router, the gate and the SEC-02 limits.
- **New environment variables (worker; for `infra/ENV.md`, platform lane):** `WORKER_PUSH_CONCURRENCY` (default 4, 1 to 32), `WORKER_PUSH_BATCH_SIZE` (50, 1 to 500), `WORKER_PUSH_PARALLEL` (10, 1 to 100), `WORKER_PUSH_POLL_MS` (500, 500 to 60000), `WORKER_PUSH_MAX_IN_FLIGHT` (2000, 1 to 100000), `WORKER_MESSAGE_MAX_IN_FLIGHT` (100, 1 to 10000), `WORKER_LEASE_MS` (300000, 60000 to 3600000), `WORKER_BUSY_POLL_MS` (1000, 100 to 60000). `WORKER_SEND_CONCURRENCY` now covers WhatsApp and SMS only. Push provider calls in flight per node = `WORKER_PUSH_CONCURRENCY` x `WORKER_PUSH_PARALLEL` (40); the worker's database pool stays 10.
- **Measured** (`local --only load --steps 5 --duration 10 --users 50 --venues 20 --bulk-push-users 15000`, same shared 4-CPU box, worker poll 500 ms). Before (quality's run): 7,799 of 15,050 sent in 388 s, then nothing; 14,506 requeues (`worker_lost`); the other 7,251 would go `dead`. After: **15,050 of 15,050 sent in 26.7 s (564 a second; 137 a second while the VUs were running)**, first push 4.1 s after the post (about 3 s of that is the fan-out), **0 dead, 0 `worker_lost`, every row on attempt 1**, never more than 2,000 in `sending`. Worker CPU 32 % of one core, Postgres 30 %.

## Done (2026-10-17: poster-render queue, contract 1.0.0-rc.5, migration 0010)

- Queue `poster-render` (`POSTER_RENDER_QUEUE`, payload `PosterRenderJob`, both from `@qc/contracts`) in `apps/worker/src/runtime.ts`: retry 3, backoff from 15 s (max 600 s), expire 120 s, dead letter `poster-render-dead`, batch 1, `WORKER_POSTER_CONCURRENCY` (default 2) per node. The worker sets the queue options with `createQueue` and then `updateQueue`, so they apply even if the API created the queue first. A malformed payload is logged (`posters.job_invalid`) and dropped. `runtime.renderPostersNow()` runs a job directly, for tests.
- Job (`apps/worker/src/posters/render.ts`, `renderPosters`): loads the job's rows that are still `queued` (with the template key), and each row's session with its venue and area. It builds the snapshot with `posterSnapshotFromSession` from the session as it is now (version = `sessions.updated_at`, area name included) and sends one `RendererRenderRequest` per group of rows that share session, template, language and fields (normally the whole job). It checks the answer with `RendererRenderResponse`/`RendererErrorResponse` and each file's sha256 and length. It stores files at `posterStorageKey(...)`, then in one transaction sets `ready`, `storage_key`, `alt_text` and `source_snapshot` (the snapshot the renderer printed), compare-and-set on `status = 'queued'`. Rows made before 0010 (no `language`) render in their `locale`.
- Failures: `failure_code` comes from `posterFailureFromRenderer`. `render_timeout` covers the client timeout (`RENDERER_TIMEOUT_MS`, default 90 s) and pg-boss's abort on expiry. `render_failed` covers a network error, an unreadable answer, a bad hash or a missing format. Retryable codes (`POSTER_FAILURE_RETRYABLE`) leave the rows `queued` and make pg-boss retry while attempts remain; only the last attempt writes `failed`, so a screen never shows "failed" for a poster still being retried. `invalid_request` and `text_too_long` fail at once. A request that cannot be built (bad fields, missing title) is `invalid_request` and the renderer is not called. Storage and database errors throw (pg-boss retries); once retries run out, the dead-letter handler fails the rows still queued with `render_failed` (`posters.job_dead`), so they never stay queued forever. That matters because `regenerate` refuses queued rows.
- Replacement: when a row with `replaces_poster_id` is ready, the old row (same session, not part of this job) is deleted in the same transaction. Its file is deleted after the commit, unless another row still points at the same key: an unchanged regeneration renders to the same content-addressed key. A failed regeneration keeps the old row and file. A failed file delete is logged (`posters.file_delete_failed`) and does not fail the job.
- Idempotent: a duplicate or a retry after success finds no queued rows and makes no renderer call. A retry after the files were stored but before the rows changed rewrites the same keys.
- Storage (`apps/worker/src/posters/storage.ts`): `PosterStorage { put(key, bytes, contentType), get(key) -> bytes | null, delete(key) }`, and `LocalDiskPosterStorage(root)` at `<POSTER_STORAGE_DIR>/<key>`. Keys must be `posters/` plus plain segments (`posterKeySegments`; `..`, absolute and odd keys are refused). Writes go to a temp file and are renamed into place. The api lane's reader should use the same interface and the same key-to-path rule.
- Config (`apps/worker/src/config.ts`), all optional: `RENDERER_URL` (http or https), `RENDERER_TOKEN`, `POSTER_STORAGE_DIR` (must be absolute), `RENDERER_TIMEOUT_MS` (1000 to 110000, default 90000, under the 120 s expiry), `WORKER_POSTER_CONCURRENCY` (1 to 8, default 2). Without the first three the worker starts, logs `posters.not_configured` with the missing names, and each poster job fails its rows with `render_failed`. That error line (`notConfigured`, `missing`) appears on every attempt and the job ends in the dead-letter queue. `missingPosterEnv(config)` lists what is missing.
- Logging: one `posters.render` line per job, counts only (`posters`, `skipped`, `ready`, `failed`, `retrying`, `replaced`, `filesDeleted`, `renderCalls`, `attempt`, `retry`), plus `failure` (the enum code, never text). No ids, names, numbers, poster text, alt text or token; a test checks this.
