### Done

- `infra/docker-compose.prod.yml` api service: `API_PROCESSES: ${API_PROCESSES:-2}`, `cpus` default `2.0` (was 1.0), `memory` default `1g` (was 512m). Health check, `stop_grace_period: 15s` (the primary kills stragglers after 12 s), networks and hardening unchanged; `init: true` passes SIGTERM to the primary, which passes it to each process. Staging (`docker-compose.staging.yml`) sets none of these, so it inherits them: checked with `docker compose -f prod -f staging config` (cpus 2, memory 1 GiB, `API_PROCESSES` "2"). An env-file `API_PROCESSES` overrides (checked with 3).
- Why `node:cluster` and not compose replicas behind Caddy: one container keeps the health check, `deploy.sh`'s health wait and rollback, the staging alias `qc-staging-api`, Caddy's single upstream and the CPU limit as they are (the limit covers all processes together); replicas would need Caddy upstream changes (Docker DNS round robin is not load balancing), per-replica limits and, above all, a shared store for the in-memory rate limits, which the cluster primary provides for free.
- Memory: production bundle (`infra/docker/bundle.sh`, esbuild 0.25.12) under the evening load at 300 VUs: workers 262 and 249 MB, primary 88 MB, 600 MB together (one process alone: 285 MB). 1g leaves room for GC peaks (each process sizes its heap from the container limit as if alone). Database connections: up to 12 per process (pool 10 + pg-boss sender 2), 24 at the default.
- Documented `API_PROCESSES` in `infra/ENV.md` (API table row and a section "API processes": defaults, sizing, connections, why the limits stay exact, replicas caveat, the open sign-in ceiling change request), `infra/.env.example` (commented, with the new `QC_API_CPUS`/`QC_API_MEMORY` defaults and a note that staging leaves them unset) and the root `.env.example`.

## Restore drill findings fixed (2026-10-18)

From `docs/quality/restore-drill.md` (quality lane, provisional local drill). Edited only `infra/backup/` and `infra/README.md`. Not committed.

- **Finding 1 (high), `--replace` destroyed live data before knowing the backup was readable.** `restore.sh` now proves the whole set first, before anything is stopped: checksums, the manifest, a full `age -d` of the dump into a private work directory (mode 700, under `TMPDIR` if set, else `QC_BACKUP_DIR`, never `/tmp` by default, deleted on exit and pruned by `backup.sh` after a day if a run was killed), `pg_restore --list` on the decrypted file (in a throwaway container from the postgres image, file mounted read-only), and a full decrypt plus `tar -t` of the poster archive. Then `--replace` restores into a new database `qc_restore_new` and compares it with the manifest **while the stack keeps running**; only then it stops api and worker, takes the `pre-restore` backup, unpacks posters into `.restore-new` inside the volume, swaps the poster files by renames (undone on failure; a `.restore-swapping` marker tells the undo which phase it reached), and swaps the databases in one transaction (`qc` to `qc_before_restore`, `qc_restore_new` to `qc`). A failure before the swap leaves live data untouched and starts the stack again. `qc_before_restore` is kept until `restore.sh --cleanup` (new) or the next `--replace`. On failure: a `RESTORE FAILED` line with the step and whether live data was touched, an alert through `QC_ALERT_WEBHOOK_URL` (`alert` in `lib.sh`, as backups use), and, after the swap, the exact command to restore the `pre-restore` file. `--replace` refuses to start without a running stack (new server: deploy first) or with a `.restore-old` left by an interrupted run.
- **Finding 2 (medium), optional checksums.** `.sha256` is mandatory in `restore.sh` (both modes) for the dump, the poster archive and the manifest; `--allow-missing-checksum` only for old backups. The hash is now compared directly, not with `sha256sum --check`, which trusted the file name inside the `.sha256` (a `.sha256` naming a different, good file let a damaged file pass; test D). `restore-test.sh --remote` lists and fetches every file of the set without `|| true`; a failed download fails the test. It passes both `--allow-missing-*` flags on.
- **Finding 3 (medium), `--check` compared counts with nothing.** `backup.sh` writes `<name>.manifest` (+ `.sha256`) with each set: `format`, `backup <name>`, `table <name> <rows>` for every public table, `posters <files>`. Counts only. The row counts come from the same snapshot `pg_dump` uses: one read-only REPEATABLE READ psql session (a bash coprocess) exports its snapshot, `pg_dump --snapshot` dumps it, and the same session counts afterwards; the poster count comes from listing the archive stream on its way to `age` (a FIFO). Manifests follow the dumps into `weekly/`, the second location and retention. `restore.sh` validates the manifest's format, then fails on any table or count that differs (prints the differing names and counts only), on a poster count that differs, and on a poster archive that is missing while the manifest lists posters. `--allow-missing-manifest` only for old backups.
- **Findings 4 and 5 (low).** Every `restore.sh` run (check, replace, cleanup) ends with one `RESTORE OK` / `RESTORE FAILED` line and the time. `restore-test.sh --remote` uses a private mode-700 directory (TMPDIR respected, else `QC_BACKUP_DIR`), and now also reports FAILED (file and alert) when it fails before the check (for example nothing found in the second location), which it did not before.
