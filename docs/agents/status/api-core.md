## Done (2026-10-17: contract 1.0.0-rc.5, posters, migration 0010)

- The five `adminPosters.*` endpoints are served by `apps/api/src/modules/posters/` (`routes.ts`, `service.ts`, `storage.ts`, `queue.ts`, `runtime.ts`); the registry (95 operations) minus `auth.*` is fully mounted again.
- `templates`: `ctx.qualify('poster.create')`, active `poster_templates` rows ordered by key, with `provisional`.
- `create`: unknown session `ctx.missing` (staff 404, outsiders 403); `ctx.authorize('poster.create', session venue)` **before** the template lookup, so an outsider learns nothing about template keys; unknown or inactive `templateKey` `ctx.unknownRef` (`not_found`); a format the template does not offer `validation_failed` `{path: 'formats', code: 'invalid_value'}`. One transaction: snapshot via `posterSnapshotFromSession(loadSessions(...), sessions.updated_at ISO, venue area name)`, one `queued` row per format (`language`, `locale = posterLocaleOf`, parsed `fields` with defaults, `source_snapshot`, `created_by`, `created_at` = request clock), one `poster.create` audit row (entity the session; meta: poster ids, template key, language, formats; no typed text). Then the job.
- **Queue choice.** The API had no pg-boss code (it hands messages to the worker through `message_outbox` rows, which do not fit render jobs), and `pg-boss` is not an `@qc/api` dependency. So `modules/posters/queue.ts` defines a `PosterQueue` port and `pgBossPosterQueue(boss)`, which calls `boss.send(POSTER_RENDER_QUEUE, PosterRenderJob)` on any object shaped like `PgBoss#send` (structural type, no import). The job is sent right after the commit (the contract and the orchestrator allow "or right after commit") with no send options, so the worker always finds the rows; retry, expiry and dead letter are the worker's queue policy. The create-time `source_snapshot` is a placeholder: the worker renders the session as it is when the job runs and overwrites the snapshot with what it printed, so `outOfDate` compares against the printed one. If the send fails (or the server never wired a queue), the new rows are set `failed` / `render_failed` and returned that way, so nothing waits forever and Regenerate works. No raw SQL into pg-boss's tables.
- `list`: `poster.read`, newest first (same-request rows in `POSTER_FORMATS` order), `outOfDate` from `posterOutOfDate(row snapshot, current snapshot)` or null, `fileUrl` = `/v1/admin/posters/{id}/file` only when `ready` with a storage key, `failureCode` only when failed, `altText` only when ready. Rows from before 0010 (no `language`) use `locale`; a row whose stored fields or snapshot no longer parse is left out with a warning (ids only) rather than failing the list.
- `regenerate`: `poster.create` at the poster's session's venue; `queued` is `conflict`; a template retired since is `not_found` (choice: same rule as create); new queued row with the same template, language, format and fields, a fresh snapshot and `replaces_poster_id`; one `poster.regenerate` audit row (entity the new poster; meta: session, replaced poster, template key, format); same queue handling. The old row stays (the worker deletes it once the new one is ready).
- `file`: `poster.read`; not `ready` (or no storage key) is `conflict`; bytes from the poster store, `Content-Type` `image/png` (story, link preview) or `application/pdf` (A4, A3) from the format, `Content-Disposition: attachment; filename="poster-<template>-<format>.<png|pdf>"` (the mock's name), `x-content-type-options: nosniff`, `cache-control: private, no-store`. A ready row whose file is gone is `not_found` (warning with the id only, never the key).
- **Storage.** Read-only `PosterStorage { read(key) }` and `localDiskPosterStorage(root)`, rooted at `POSTER_STORAGE_DIR` (`posterStorageFromEnv`; unset or blank: `<os tmpdir>/qc-posters`). The key-to-path rule mirrors the worker's `apps/worker/src/posters/storage.ts` exactly (`posterKeySegments`/`resolvePosterPath`): file at `<root>/<key>`, only `posters/...` keys of plain segments (one extension on the last), no `.`/`..`, no absolute key, at most 300 characters, absolute root only. The API never writes (production mounts the volume read-only); the test harness plays the worker with `h.putPosterFile`.
- **Wiring.** (Superseded by "poster queue wiring" above: now `AppDeps.posters`.) `providePosterRuntime(db, { storage, queue })` set the store and queue per database handle in a `WeakMap`; without it the app used `posterStorageFromEnv()` and a queue that refuses every job.
- Route binder (`modules/shared/route.ts`): `application/octet-stream` success branch: the parsed `Uint8Array` is sent as is (no JSON), the handler's `content-type` kept (default `application/octet-stream`), `nosniff` added; a non-bytes result is `internal_error`. Test harness: `ApiResult.bytes`, the contract check accepts a file response (non-JSON type, bytes pass the schema), and each harness has a temp poster folder (removed on `close`) and an in-memory queue (`h.posterQueue`, emptied on `reset`).
- Leftover fixed: the `apps/api/src/jobs.ts` comment now says `purgeStaleAuthRows` lives in `@qc/db` and the worker runs it at 03:00 Pakistan time (the API re-exports it); the stale question below is removed.
- Tests: new `src/test/posters.test.ts` (42: templates by role and inactive rows; create happy path with the exact snapshot and job, bilingual locale, audit meta and logs without typed text, unknown/inactive template, scope before template, format not offered, contract body refusals, unknown session by role, out-of-scope coordinators, in-scope coordinators, queue failure then regenerate, one-off lecture; list order, file link and failure code, per-session, out of date on time via `changeSchedule`, on venue via `adminVenues.update` but not on a title change, both reasons, unknown and out of scope; regenerate conflict, fresh snapshot and replaced id, audit, failed poster, retired template, unknown and out of scope; file PNG and PDF bytes and headers, queued/failed conflict, missing file, unknown and out of scope, typed client returns `Uint8Array`; key rule identical to the worker's (bad keys, relative root), read-only disk store, env root; pg-boss sender shape, refused send, runtime fallback, unwired queue). Scope matrix: five new scenarios (templates by "holds `poster.create` anywhere", create, list, regenerate, file against a ready stored poster) for all eight caller kinds, plus the national-admin happy path. The 4 previously failing tests (3 in `contract.test.ts`, 1 in `scope-matrix.test.ts`) pass with no expectation changed. `@qc/api` 661 passing in 31 files (was 610 passing and 4 failing); typecheck, eslint and prettier clean on `apps/api`.

## Design notes

- Error policy. `missing(action)` answers `forbidden` for people with no qualifying role and `not_found` for staff (only on endpoints with params). `unknownRef(action)` is for body fields that point at nothing: `forbidden` for outsiders, `not_found` for anyone holding a qualifying role. Since rc.3 the scoped export follows the same rule for its `cityId` and `venueId` filters. `conflict` is returned only where the contract declares it.
- A handover whose `replacesAssignmentId` names an assignment at another place, or a revoked one, answers `not_found` (the same as unknown), so a coordinator learns nothing about other places. Replacing yourself is `validation_failed` on `replacesAssignmentId`.
- `adminUpdates.list` reports `recipients` as the current reach (the number is not stored per post).
- Attendance `markedAt` is derived (no column).
- Programs are upserted lazily, so no seed is needed.
- Roles, invites and account deletion overlap with the auth lane (sign-in consumes invites; deletion cascades). The handlers share the tables and the role-resolution helpers.

## Questions for the orchestrator

- Auth lane: `modules/auth/me.ts` `loadMe` (the `Me` in the sign-in response) does not send `profile.dailyGoal` or `profile.memorisationReviseAfterDays`. They are optional in the type so it still parses, but the rc.4 changelog says the server always sends them; `me.get` does. The auth-scopes lane should add the two fields (same mapping as `modules/me/profile.ts`).
- The `reading_days`, `community_today`, `ayah_of_the_day` and `memorisation` flags are not enforced by the API: the contract has no error code for a feature that is off, so the endpoints always answer and the apps hide the features by flag. Say if the API should refuse instead (that needs a contract change).
- The worker creates the `poster-render` queue (it does, in `startRuntime`); the API never creates it, so posters made before the worker's first start come back `render_failed` (Regenerate works). Both services need the same `POSTER_STORAGE_DIR` (compose sets it).
- The lazy per-session `topUpOccurrences` on the public occurrences view and `insertSession` still ignore a season's last day (pre-existing); only the daily job caps at it.
- Import duplicate keys follow the contract text and the mock (venue: city + English name, case-insensitive; session: venue + English title + kind + start time + days or date; coordinator: number + role + place, or a person who already holds it), not the brief's wording (venue by city + area + name, session by venue + weekday + time). Say if the brief's keys are wanted.
- `message_templates` rows are not seeded by the API. `adminTemplates.list` returns what is in the table.
- `index.ts` environment variables: `DATABASE_URL` (required), `PORT` (default 3000), `CORS_ORIGINS` (comma list), `TRUST_PROXY=true`, `PUBLIC_WEB_BASE`, `POSTER_STORAGE_DIR` (poster files, read-only), plus the auth lane's `APP_ENV`, `AUTH_SECRET`, `AUTH_FIXED_CODE`, `AUTH_TRUST_PROXY` and the `@qc/messaging` provider variables.
