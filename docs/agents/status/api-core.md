## Done (2026-10-18: named prepared statements, change request `api-named-statements`)

- **Reviewed the patch and applied a safer version** (`apps/api/src/db.ts`: `nameStatements`, `StatementNames`, `isNamable`, `isStaleStatementError`). Problems in the patch:
  - Its 64-parameter limit never applied, because drizzle passes values as the second argument of `client.query`.
  - It named BEGIN, COMMIT and ROLLBACK.
  - It had no recovery from "cached plan must not change result type". On real Postgres 16 even widening a varchar's length triggers that error, and inside a transaction the connection kept failing the statement.
  - Its memory estimate was low: about 100 kB per named statement measured, so its 500-per-connection cap could reach about 1 GB for 20 connections.
- **Applied rules:**
  - Name only statements with 1 to 64 parameters, `IN` lists of at most 20, and no multi-row insert, from their third use on a connection.
  - At most 64 named statements per connection.
  - A stale statement is prepared again under a new name; one failed call per connection and statement.
  - Pool `maxLifetimeSeconds: 3600`.
  - The worker's pool and PGlite are not affected.
- **Risks checked:**
  - Generic plans: 14 hot statements, 40 real parameter sets each, plus a skewed venue. Only `home_next` has a bad generic plan (10.5 ms against 0.63 ms), and auto mode never picks it (estimated 413 against 15.75).
  - Deploys always restart the API after `migrate`.
  - Advisory locks still serialise when taken by a named statement.
  - Details are in the change request ("Applied").
- **Load, local** (`API_PROCESSES=2`, Postgres alone on one core, ANALYZE after the seed, 2 runs each), main against applied at 150 VUs:
  - Throughput: 367 and 374 req/s, then 448 and 440.
  - p95 all requests: 212 and 218 ms, then 43 and 52.
  - Postgres core: 89 % busy, then 63 to 65 %.
  - API RSS unchanged (about 560 to 620 MB for primary and 2 workers).
  - Postgres memory: API backends +3.2 MB each, about 64 MB in total.
  - Every route and the 100-VU table are in the change request.
- **Tests:** new `src/test/named-statements.test.ts`, 18 tests. A fake node-postgres client keeps server-side statements and raises the real 0A000 after a "migration". The tests cover:

## Done (2026-10-18: the API on 2 CPUs, owner decision)

- **In-memory state found.** Two limiters lived in each process's memory: `middleware/rate-limit.ts` `MemoryRateLimiter` (the contract buckets `default` 300/min, `auth_code`, `registration`, `messaging`, and the poster allowance `poster_write` 10/min) and the auth lane's `InMemoryRateLimiter` (code requests per number 5/h and per address 30/h, code checks per number and per address, refresh per address 600/10 min). With two processes each would have allowed its own full limit. Nothing else needs sharing: the route binder's `arrayKeyCache` and `time.ts`'s formatter cache are derived from code, `getAuthContext`'s cache is per process by design, the API runs no timers or schedules, idempotency is the outbox's unique key, and capacity, confirmation dedupe and poster `conflict` already run under row or advisory locks. The database-counted ceilings had a check-then-insert race (independent of the cluster, worse with it): the invite allowance (fixed here) and the sign-in code ceilings (auth lane, change request below).
- **Limits made safe, exact across processes** (`middleware/shared-limits.ts`): the cluster primary holds the one `MemoryRateLimiter` and the one `InMemoryRateLimiter` (`SharedLimitStore`) and answers worker requests over the cluster IPC channel one at a time; workers use `sharedBucketLimiter` / `sharedSignInLimiter` (`SharedLimitClient`), passed as `AppDeps.rateLimiter` and `AuthDeps.rateLimiter`, so no auth-lane file changed. Same classes, same semantics and retry times as one process. Requests are validated with Zod in the primary; a refused, unanswered (5 s) or closed channel fails the call (500 `internal_error`), never skips the limit. Keys are the limiters' own (user ids, hashed addresses). Chosen over Postgres: no migration in `packages/db`, no extra write per request, no new personal data at rest. Limits still reset when the container restarts, as before; several containers would need a shared store (said in `infra/ENV.md`).
- **Invite allowance (SEC-03) exact under parallel requests**: `assertInviteAllowance` (`modules/roles/service.ts`) takes `pg_advisory_xact_lock(hashtext('invite_allowance:<actor>'))` first; `createInvite` now checks the allowance before retiring lapsed invites, so the lock comes before any row lock. Real Postgres, 2 processes, six 40-row coordinator imports at once by one admin: 240 invites without the lock, exactly 200 with it.
- **Multi-process entry point**: `index.ts` reads `API_PROCESSES` (Zod, 1 to 8, default 1; an invalid value stops start-up naming the variable). At 1 it serves in-process exactly as before. Above 1 it is a `node:cluster` primary (`cluster.ts` `superviseWorkers`): forks N workers on the shared port, restarts a dead one after 1 s doubling to 30 s for crashes in a row (reset after 60 s of serving), treats a death before any worker served as a start-up failure (stops the rest, exits 1), and on SIGTERM/SIGINT sends SIGTERM to each worker (a signal, not `worker.kill()`, so the IPC channel stays up while requests finish), exits 0 when all stopped, SIGKILL and exit 1 after 12 s. A worker stops if it loses the primary. The server itself moved to `server.ts` (`startServer`, idempotent `stop()`), loaded lazily so the primary does not load the app (primary 88 MB RSS in the bundle). Logs carry worker ids, pids, exit codes and signals only (`exitCode`, since the logger redacts `code`).
- Tests: new `src/test/shared-limits.test.ts` (10: a bucket exact across two clients asking at once, with the same retry time as the in-process class; sign-in limits sliding and shared, refused hit not recorded, reset from the other process; malformed and foreign messages; refused, silent (timeout) and closed channel fail the call; unsendable message; no primary; two app instances on one database share the contract bucket by address (4 of 10, separate in-process limiters would allow 8), the code requests per address (3 of 8, sender called 3 times) and the refresh limit (2 of 6); 500 when the primary does not answer). ## Design notes

- Error policy. `missing(action)` answers `forbidden` for people with no qualifying role and `not_found` for staff (only on endpoints with params). `unknownRef(action)` is for body fields that point at nothing: `forbidden` for outsiders, `not_found` for anyone holding a qualifying role. Since rc.3 the scoped export follows the same rule for its `cityId` and `venueId` filters. `conflict` is returned only where the contract declares it.
- A handover whose `replacesAssignmentId` names an assignment at another place, or a revoked one, answers `not_found` (the same as unknown), so a coordinator learns nothing about other places. Replacing yourself is `validation_failed` on `replacesAssignmentId`.
- `adminUpdates.list` reports `recipients` as the current reach (the number is not stored per post).
- Attendance `markedAt` is derived (no column).
- Programs are upserted lazily, so no seed is needed.
- Roles, invites and account deletion overlap with the auth lane (sign-in consumes invites; deletion cascades). The handlers share the tables and the role-resolution helpers.

Original note: overlapping queries on one transaction client (`DeprecationWarning: Calling client.query() when the client is already executing a query`, an error from pg 9) during `POST /v1/registrations` and `POST /v1/admin/sessions/:id/schedule`. Candidates: `Promise.all` on the transaction handle in `modules/sessions/views.ts:62`, `modules/updates/publish.ts:209`, `modules/updates/reach.ts`. Not visible under PGlite.
